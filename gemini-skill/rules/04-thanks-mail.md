# お礼メールの決まり

# 商談お礼メール

商談議事録やメモから、その日の商談内容に紐づいたお礼メールを作る。
テンプレートの穴埋めではなく、**議事録から要点を抽出して構成を組む**のが本質。汎用的な「本日はありがとうございました」だけのメールは作らない。

このメールの目的は儀礼ではなく、次のアクション（部内共有・上申・申込判断）を相手が社内で進めやすくすること。

文体の基本ルールは `my-voice` スキルに従う。ここではお礼メール固有の構成と判断を扱う。

## 進め方

「読む → 型を判定して根拠を示す → 書く → 確認事項を出す」の順で進める。

**初回の使用時のみ、担当者情報を確認する。**
このスキルは複数の営業担当が使うため、名前とZoom情報がスキル内に固定されていない。
会話の中でまだ聞いていなければ、書き始める前に確認する（詳細は `「1 書き方の決まり」の fixed_info.md`）。
一度聞いたら、その会話の中では繰り返し聞かない。


**要点の事前確認はしない。** 先に草案を出して、フィードバックで直す前提で進める。
「要点はこの3つでよいですか」と聞いてから書くのは往復が増えるだけなので避ける。
ただし型の判定根拠は本文の前に2〜4行で示す。ここを外すと全部書き直しになるため。

固定値（件名・宛名の書式・資料リンク・Zoom情報・プラン体系）と、サービス概要の書き方は
`「1 書き方の決まり」の fixed_info.md` にある。書き始める前に必ず読む。

### Step 1: 議事録を読んで材料を抽出する

議事録・きんぼっとのトランスクリプト・メモを読み、下の項目を拾う。
きんぼっとの自動文字起こしは誤変換が多い（社名・人名・固有名詞が特に崩れる）。**社名と担当者名は誤変換を疑い、確信が持てなければ確認する**。

**型F（資料送付）の場合、入力は議事録ではない。**
必要なのは「何を送るか（URL・ファイル名）」「いつ誰との場で使うものか」「前回どんな修正を依頼されたか」の3点。
これらは会話の履歴か、あんちゃんの指示から取る。足りなければ聞く。

拾う項目：

| 項目 | 何のために拾うか |
|---|---|
| 会社名・担当者名・部署 | 宛名 |
| **商談が何回目か** | 型Cで概要を入れるかの判断／「本日は」か「本日も」か |
| **先方の参加人数** | 宛名に何名並べるか／「皆様の貴重なお時間」を使うか |
| 顧客が自分の言葉で語った課題・状況 | 本文の課題パートの素材。営業側が言った一般論ではなく顧客の発言を使う |
| 顧客が出した懸念・疑義（Why型の質問） | 本文でアンサーを返す対象。ここが最重要 |
| 顧客が語った期日・時期 | スケジュールパートの根拠 |
| 決裁フロー（誰→誰→誰） | 次のアクションの粒度を決める |
| 商談中に約束した提供物 | リンク・添付・追加資料の一覧 |
| **前回依頼したものを受領済みか** | 冒頭にお礼を追加するかの判断 |
| 次回商談の日時・形式（Zoom／対面） | 次回打ち合わせブロック |
| 顧客の温度感を示す発言 | 押しの強さを調整する材料 |

商談回数は議事録の冒頭で分かることが多い（「前回8月6日に」「改めてお時間いただいて」など）。
判断がつかない場合はあんちゃんに確認する。回数を誤ると概要の有無を間違える。

抽出できなかった項目は空欄のまま扱う。**議事録にない事実を推測で埋めるのは禁止**。特に次回日時・URL・金額・決裁日は創作しない。

### 曜日を推測で書かない

**議事録に曜日の記載がない場合、日付だけを書く。**
日付から曜日を計算して補完しない。計算は高確率で外れる。

- ○「8月24日 10:00～」（議事録に曜日がない場合）
- ×「8月24日（木）10:00～」

議事録に曜日が明記されている場合のみ、その曜日をそのまま書く。
曜日を入れたい場合は、確認事項として「曜日が正しいかご確認ください」と添える。

**実際に事故が起きている。** 8月24日を「日」と書いて送信し、訂正メールを出すことになった。
曜日は日付の一部のように見えるが、推測で埋めている以上は創作と同じ。

誤変換が激しく顧客の発言の趣旨が判別できない箇所は、**その論点を本文で使わない**。
文脈から意味を補って本文に書くと、言っていないことを言ったことにしてしまう。
その論点が本文の骨格に必要な場合は、確認事項として挙げる。

### Step 2: 要点を絞る

本文で伝える要点は **3つまで**。4つ以上入れると読まれない。
選ぶ基準は「営業側が言いたいこと」ではなく **「顧客が引っかかっていたことに答えているか」**。

顧客が出した懸念に本文で答えていないお礼メールは失敗。例：
- 「ChatGPTとの棲み分けは？」→ サービスの位置づけパートで答える
- 「情報を出しすぎると担当者と話す必要がないと思われないか」→ サービスの位置づけパートで答える
- 「システムに頼らず自分の足で来る人と働きたい」→ 「会わせるためのサービス」という再定義で答える
- 「どれくらいの人に届くのか」→ 母数の構造的な話で答える

会話の中であんちゃんから要点が指定されていれば、それを優先する。

### Step 3: 型を選ぶ

商談の結果で本文の骨格が変わる。`「1 書き方の決まり」の templates.md` を読んで該当する型を使う。

| 商談の結果 | 使う型 |
|---|---|
| 初回商談 → 案件化（今月／来月判断＋再商談設定済） | A: 初回商談・案件化 |
| 初回商談 → 判断保留（再商談が未設定、10日ルール中） | B: 初回商談・再商談未設定 |
| 再商談（上申準備）実施後 | C: 再商談・上申準備 |
| 受注後 | D: 受注後・キックオフ前 |
| 見送り・失注・情報収集段階で「今ではない」と言われた | E: 見送り・タイミング未達 |
| **商談後、約束した資料・見積書・動画などを送る** | **F: 資料送付・約束履行** |

初回商談でも、顧客が冒頭から「情報収集の段階」と明言していたり、
社内制約（セキュリティ・機密・予算）で導入判断ができないと示された場合は型Eを使う。
型Aで書いて後半だけ見送りに寄せると、押しの強さが噛み合わない。

**型Fだけはお礼メールではない。** 商談当日ではなく後日、約束したものを送るためのメール。
議事録ではなく「何を送るか」が入力になるため、A〜Eとは骨格が違う。
「資料送って」「見積もり送るメール書いて」のような依頼が来たら型Fを使う。

### Step 4: 書く

完成品の基準となる実例：

- 型A → `「1 書き方の決まり」の example_initial_meeting.md`
- 型C（2回目・概要あり） → `「1 書き方の決まり」の example_followup_meeting.md`
- 型C（3回目以降・概要なし） → `「1 書き方の決まり」の example_repeat_meeting.md`
- 型E → `「1 書き方の決まり」の example_declined.md`
- 型F → `「1 書き方の決まり」の example_document_send.md`

該当する型の実例を読んでから書く。長さ・改行位置・押しの強さをそこに合わせる。

書き終えたら、出力する前に本文を1文ずつ見て次を確認する。

- 「〜します」「〜いたします」と書いた自分側のアクションは、すべて議事録に発言があるか
- 会社名・担当者名・日付・URL・金額は、すべて議事録または指定に根拠があるか
- **曜日を書いている場合、議事録にその曜日の記載があるか**（計算で補完していないか）
- 1文が2行以上にまたがっていないか

1つでも根拠がないものがあれば、その文を消す。埋め合わせない。

### Step 5: 確認事項を出す

メール本文のあとに、確認が必要な点を挙げる。毎回チェックするのは：

- リンクの最新版（概要資料・デモURLは差し替わることがある）
- 誤変換が疑われる社名・人名
- 議事録から拾えなかった項目（次回日時、Zoom URL など）
- スケジュールの表現を柔らかくするかどうか（顧客が「確定できない」と言っていた場合）

## 本文の構成原則

### 骨格は「構造化 → 示唆 → 位置づけ」

1. **課題の構造化** — 相手の課題を「個社特有の問題ではなく構造的な問題」として言語化する。相手を責めない。逃げ道を作る。
2. **示唆** — だからこそ何に注力すべきか。フレームで示す（例：採用力＝認知度×選ばれる力）
3. **サービスの位置づけ** — DOCを「効率化ツールではなく〇〇のためのサービス」として再定義する。ここで顧客の懸念に答える。

この3段は初回商談（型A・B）で使う。再商談以降（型C以降）は、この骨格を繰り返さず**合意事項の確認と次のアクション**に軸を移す。同じ説明を2回送らない。

### 上申の負担を相手に寄せない

「ご共有ください」で終わらせず、自分が何をするかを書く。

- ○「西内様が社内でご説明しやすい形の資料をご用意してお送りいたします」
- ○「私自身も事前に社内で交渉を進め、スケジュールに間に合う形で動いてまいります」
- ×「社内でご検討のうえ、ご連絡をお待ちしております」

### スケジュールは相手の発言に合わせて強度を変える

顧客が期日を自分の言葉で語っていれば、その日付を本文に書いてよい。
顧客が「確定はできない」「可能性はある」と留保していた場合は「〇月〇日を一つの目安に」と柔らかくする。相手が言っていない締切を作らない。

### 書かないもの

**最優先の禁止事項：商談で言っていない約束を書かない。**
「随時情報をお送りします」「社内で確認してまいります」「別途ご提案をお持ちします」のような
**自分側のアクション**は、商談中に実際に口にしたものだけを書く。
議事録に該当する発言がなければ書かない。文章として自然に見えても捏造は捏造で、
送ったあとに実行を求められるので実害が出る。

他に書かないもの：

- 金額・キャンペーン条件（口頭と資料に任せる。本文に書くと値引き交渉の起点になる）
- 議事録に出ていない他社事例・実績数値
- 商談で答えられなかった質問への、その場しのぎの回答（調べてから別便で送る）
- 「ご連絡をお待ちしております」「ご検討のうえご返信ください」＝相手にボールを預けて待つ表現。
  ただし追わない案件では「次はこちらから追う」とも書かない。
  正解は **「またご検討されるタイミングがあればよろしくお願いします」** のように、
  相手を待ち構えず・こちらも約束せず、次の接点を開いたままにする書き方。

### 箇条書きは「これから動くこと」だけにする

**修正や対応が発生しない項目はリストに載せない。**
「現状のボリュームで問題なし」「特に修正なしとのこと」のような、
確認しただけで何も動かない項目は削る。リストが長くなるほど読まれなくなる。

**括弧内の補足も、相手が判断に使わないものは削る。**
商談中の会話で共有済みのニュアンスをメールで再説明しない。

- ○「お見積書」
- ×「お見積書（御社名を記載したもの）」← 当日その場で確認済み
- ○「サービス紹介動画」
- ×「サービス紹介動画（ご案内中のプラン部分の再生時間を明記します）」← 送るときに書けばよい
- ○「事例は1社ではなく2〜3社あるとよい（SES・30名規模程度）」← 規模の条件は次の作業に必要なので残す

判断基準は「この括弧を読まないと相手が困るか」。困らなければ削る。

### 依頼は断定せず、自分の意図として述べる

相手に何かをお願いする文は、要求の形にせず自分がどう考えているかを述べる。

- ○「お手間をかけないように進められたらと考えておりますので、遠慮なく私に振っていただけたらと思います」
- ×「お手間をかけたくないので、遠慮なく私に振っていただけますと幸いです」
- ○「部内でご共有いただけるとうれしいです」
- ×「部内でご共有をお願いいたします」

### 「本日」を重複させない

冒頭で「本日はお忙しい中〜」と書いているので、直後の段落で再び「本日ご相談させていただいた内容」と書くと重複する。
2回目以降は「打ち合わせにてご相談させていただいた内容」のように言い換える。

### 上申先が読む前提なら、担当者個人に閉じない

上申・部内共有が想定される場合、本文が担当者一人の話に見えないようにする。

- ○「関川様や担当の方にお会いする前に離脱されている状況にあります」
- ×「関川様にお会いする前に離脱されている状況にあります」

### 前回のメールと同じ言い回しを繰り返さない

同じ相手に短期間で複数のメールを送るとき、前回使った定型的な一文をそのまま使い回さない。
2通続けて同じ表現が出るとしつこく、テンプレートを貼っているように見える。

特に繰り返しやすいのは、締めの直前に置く「依頼」の一文。

- 1通目で「資料の添削でお手間をかけないように進められたらと考えておりますので、遠慮なく私に振っていただけたらと思います」を使った
- → 2通目では使わない。「ご確認いただいて修正が必要な点があればお知らせください」だけで足りる

**型Fを書くときは、直前に送ったお礼メール（型C等）の本文を確認する。**
会話の履歴にあれば読み、なければあんちゃんに「前回どう送ったか」を聞く。

### 冒頭は商談回数と参加人数で書き分ける

**2回目以降の商談なら「本日は」ではなく「本日も」。**
複数回時間をもらっている関係が伝わる。

**複数名が参加していれば「皆様の貴重なお時間」。**
誰の時間をもらったのかを明示する。

```
本日もお忙しい中、皆様の貴重なお時間をいただき誠にありがとうございました。
```

**前回依頼した提供物を受領していれば、お礼を1文追加する。**
前回の依頼が果たされていることへの応答になる。

```
また、Web制作関連職種の最新の数字につきましても、早速お送りいただきありがとうございました。
```

### 整理して送る前に、動機を一文置く

合意事項や修正点を並べる前に、なぜ整理して送るのかを一文添える。
これがないと事務的な議事録送付に見える。

```
少しでも[担当者名]様のお力になれたらと思い、
打ち合わせにてご相談させていただいた内容を、あらためて整理してお送りいたします。
```

## 体裁

- **件名を必ず付ける。** 定型文は `「1 書き方の決まり」の fixed_info.md` にある（型Fのみ送付物が分かる件名にする）
- 宛名は会社名を1行目、担当者名を2行目。複数名は全角スペース区切りで1行に並べる
- 1文＝1行。意味の切れ目で改行する。モバイルで読まれる前提
- **同じ記号のブロックを連続させない。** `＝＝＝` の次に別のブロックが来る場合は `ーーー` を使う
  （例：スケジュールを `＝＝＝`、次回打ち合わせを `ーーー`）
- リンクは `ーーー` の区切り線ブロックで囲む
- 冒頭は「いつもお世話になっております。ネオキャリアの[担当者名]です。」
- 締めは「本日は誠にありがとうございました。」＋「引き続きどうぞよろしくお願いいたします。」＋署名
- 役職名に「様」を付けない（○「役員の方」／×「役員様」）
- 出力はプレーンテキスト。HTMLやファイルにしない（そのままGmailに貼る）

## このスキルの検証状況

型A・C・E・Fは実際の商談で使って修正済み。型B・Dは未検証。

型Dを使うときは、受注後の実際のフロー（初期設定・学習・CS担当の引き継ぎ）と
テンプレートの内容が合っているかをあんちゃんに確認してから書く。
テンプレートの記述が実態と違う場合は、そのまま使わずに指摘する。
